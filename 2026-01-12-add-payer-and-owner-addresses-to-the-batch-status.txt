⏺ StampsRegistry Contract Analysis

  This is a proxy/registry contract for Swarm Postage Stamps that enables batch gifting - allowing one person to pay for stamps that are owned by someone else.

  Key Concepts

  What's happening:

  1. Proxy Pattern: StampsRegistry sits between users and the original PostageStamp contract
  2. Batch Gifting: Separates the payer (who funds) from the owner (who receives the batch)
  3. Registry: Tracks additional metadata not stored in the original contract

  Architecture

  User (Payer) → StampsRegistry → PostageStamp Contract
                       ↓
                Stores payer info

  Key Differences from PostageStamp

  | Feature       | PostageStamp       | StampsRegistry               |
  |---------------|--------------------|------------------------------|
  | Owner = Payer | ✅ Always the same | ❌ Can be different          |
  | Tracks payer  | ❌ No              | ✅ Yes (batchPayers mapping) |
  | Use case      | Direct purchase    | Gifting/proxy purchase       |

  Core Functionality

  1. createBatchRegistry (lines 237-303)

  The main batch creation function with gifting support:

  function createBatchRegistry(
      address _owner,        // WHO PAYS (msg.sender transfers tokens)
      address _nodeAddress,  // WHO RECEIVES (actual batch owner)
      ...
  )

  Flow:
  1. Payer (msg.sender) transfers BZZ tokens to StampsRegistry
  2. StampsRegistry approves PostageStamp contract to spend tokens
  3. StampsRegistry calls PostageStamp.createBatch with _nodeAddress as owner
  4. Stores _owner as payer in batchPayers mapping
  5. Stores full batch metadata in ownerBatches[_owner] array
  6. Emits BatchCreated event with both owner and payer

  This is why you see:
  - owner = node address (who owns the batch)
  - payer = msg.sender (who paid for it)

  2. Event Structure (lines 95-104)

  event BatchCreated(
      bytes32 indexed batchId,
      uint256 totalAmount,
      uint256 normalisedBalance,
      address indexed owner,    // Node that owns the batch
      address indexed payer,    // Person who paid for it
      uint8 depth,
      uint8 bucketDepth,
      bool immutable_
  );

  This explains the data you're seeing in your database - the events contain both addresses!

  3. Batch Management

  - topUpBatch: Anyone can top up, but registry tracks original payer
  - increaseBatchDepth: Only the payer can increase depth (owner-gated)

  4. Data Storage

  Two key mappings:
  mapping(bytes32 => address) public batchPayers;      // batchId → payer
  mapping(address => BatchInfo[]) public ownerBatches; // payer → all batches they paid for

  Why This Exists

  Use case: Beeport UI or other services can:
  1. Accept payment from User A
  2. Create a batch owned by User B (their node address)
  3. User B gets the storage, User A paid for it
  4. Track who paid for what (accounting, analytics, gifting)

  Your Database Context

  - 16,139 PostageStamp batches: No payer field (direct purchases)
  - One address received 66 batches from 19 payers = batch gifting in action

  Security Notes

  - Only the payer stored in batchPayers can increase depth (line 373)
  - Admin can update the PostageStamp contract address (upgradability)
  - Admin can migrate old batch data (lines 187-225)
